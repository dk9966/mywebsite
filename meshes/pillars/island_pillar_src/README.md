# Island pillar — procedural mesh and texturing

Everything about the island pillar is generated by these scripts: the geometry
as well as the look. No Blender, no hand-painted maps, no input files at all.
The output is `../island_pillar.glb`.

```
python build_pillar.py      # generate + texture -> island_pillar.glb
python validate.py          # structural checks on the exported glb
python render_preview.py    # -> ../island_pillar_preview.png
python render_shell.py      # -> ../island_pillar_shell.png (raw geometry, fast)
```

```
python build_pillar.py --all   # all three size variants
python validate.py --all       # check all three
python scan_mesh.py            # audit the mesh for artefact sources
```

## The mesh

The pillar used to be an imported mesh: a core cylinder with a few hundred
rectangular slabs scattered around it and exported as a union that had never
been booleaned. That one decision caused most of the problems this README used
to be about.

- **Gaps.** Two neighbouring slabs share no vertices, so the seam between two
  ribs is a real hole. Vertically the slabs are continuous because a rib *is*
  one tall box, but horizontally there is nothing between them — you can see
  straight through, most obviously around the top platform ring.
- **Overlaps.** Where slabs intersect, ~40% of the faces end up buried inside
  the solid, many of them exactly coplanar with a visible face, which z-fights.
- **Intersections.** The crenellation ring was another set of boxes dropped on
  top of the haunch, meeting it at arbitrary angles.

None of that is fixable downstream, and the pipeline had grown two expensive
passes trying: a winding-number search for buried faces and a coincident-plane
nudger. A gap between two boxes is *missing surface*, and no post-pass can
invent it.

`shape.py` builds the surface instead of the solid. The whole pillar is one
function of two variables sampled on a grid of angular columns × height rows:

```
R(theta, y)  ->  the radius interval the pillar occupies there
```

A cell is not a box; it is a piece of the surface, and its four sides are shared
exactly with the four cells around it. Three kinds of face come out of that: the
cell's own outer (and where hollow, inner) panel; a **theta wall** covering
exactly the radii where one column is solid and its neighbour is not; and a
**y wall** doing the same across a row boundary, which is every ledge plus both
end caps. Walls are set differences, so a step is emitted once and spans the
whole gap. Watertight by construction, and nothing is ever buried.

The rest is watertightness bookkeeping. Where four cells meet, the four walls
around that corner all end on one radial line; each wall edge landing there is
split at the same set of radii — the endpoints of all four cells. Inside any
elementary interval between two of those radii all four cells are then uniformly
solid or empty, so walking the four-cell cycle the number of solid/empty flips
is necessarily even and every sub-edge is shared by exactly two faces. That
turns "closed" into "manifold", and rules out the T-junctions that would
otherwise sparkle. Depths also snap to a `quantum` grid so two blocks whose
jitter lands a ten-thousandth apart merge instead of growing a sliver wall
between them.

The features are all variations in `R`, not separate objects: rib groups that
share a depth (so a rib is one face, not several), recessed channels, a closed
plinth at the foot, per-group block breaks that stagger the block ends between
neighbours, and one closed collar row at the very top — the only place every
column is forced to the same radius, so the shell's top boundary is one clean
circle for the paving to weld against. There is deliberately nothing *above*
the platform: the raised block ring this design went through first read as
castle battlements, then as a parapet, and both versions were fighting the
reference, whose tops are just a brick disc running flush to the edge.

The angular resolution is an *output*: ribs and channels are given widths in
columns and the circle is cut to fit, so `ribs × (rib_cols + gap_cols)` decides
the facet count (65 at the current settings). Height rows are packed tighter
toward both ends, where the profile turns hardest and the blocks are smallest.

The silhouette is a monotone cubic through `SHAPE.profile` keypoints. Monotone
matters: a Catmull-Rom through the same points overshoots and puts a bulge just
above the waist.

`validate.py` asserts the surface closes — zero boundary edges — which is the
check the whole rewrite exists to pass. Seven edges are used by more than two
faces, where two blocks meet corner to corner across a diagonal; that is real
geometry, not a defect, and the surface stays closed through it.

## Size variants

Three files, sized from the concept art rather than from round numbers. Island
deck widths measured off that render, in pixels: CONTACT 230, EXPERIENCES 260,
minecraft 280, WORKSHOP 345, ABOUT ME 350, central 480-570. So the central
island is roughly **2.4x** the smallest side island — nowhere near the 5x a
first guess suggested.

| file | role | tall | plinth | waist | deck | waist/plinth |
| --- | --- | --- | --- | --- | --- | --- |
| `island_pillar.glb` | small side island | 6.0 | 2.48 | 1.46 | 2.08 | 0.59 |
| `island_pillar_large.glb` | mid island | 6.6 | 3.74 | 2.41 | 3.12 | 0.64 |
| `island_pillar_huge.glb` | central island | 7.5 | 6.02 | 4.00 | 4.98 | 0.66 |

**Profile shaping.** Scaling width alone keeps the hourglass proportions fixed,
so a bigger variant stays exactly as pinched as the small one. Two opposite
controls fix that, both a radius multiplier that varies with height:

- `fill` fattens the **waist**, leaving the ends alone — `1 + fill` at mid
  height, exactly 1.0 at top and bottom.
- `flare` does the reverse, pushing the **ends** out for a deeper hourglass.
  Currently 0 on every variant, but kept: it is the same machinery.

The amount and the power interact in a way that is easy to get wrong. A large
fill on a low power peaks hard at mid height and the pillar grows a belly, so
the build prints a `mid bulge` figure — how far the middle bows past the ends of
its own span — to make that measurable rather than a matter of squinting. It is
read at the 85th percentile of radius rather than the maximum: the shell's ribs
step in and out block to block, and on the maximum the widest *vertex* in a band
says which block happened to jut, not where the silhouette runs. On the maximum
this reported a belly on a pillar with no fill applied at all.

The result keeps the hourglass read at every size — waist/plinth 0.59 → 0.64 →
0.66 — while the huge variant's waist is 2.7x the base pillar's in absolute
terms, so it is a substantial mass rather than a thin neck.

Both the stretch and the flare are applied to the generated shell **before
anything else runs**, so every measurement, threshold and UV is computed on the
real final shape. Doing it at export instead would go wrong two ways: non-uniform scaling
needs the inverse transpose to keep normals correct, and UV1 holds distance/band
*ratios*, so a stretched export would draw edge lines at different widths
depending on whether an edge ran vertically or horizontally.

`scaled_params()` rewrites every world-unit threshold to match: heights follow
the height factor, radii follow the width factor, and small feature sizes (band
widths, probe distances, tie-break offsets) follow the geometric mean of the
three axes — they are not aligned to any single axis, and using width alone
would leave detail on the huge variant noticeably coarse.

Each variant re-runs the whole pipeline rather than reusing the base result, so
the smoothing groups, sharp-edge detection and UVs are recomputed for the new
proportions. The shell itself is generated from the same seed, so all three are
the same pillar at three sizes. Triangle counts do differ (9116 / 11492 /
18284) for exactly one reason: the paving. Its bricks are a fixed world size,
so a wider platform gets more of them — which is also why the stretch happens
inside `shape.build` rather than by scaling positions afterwards; the paving
has to see the final radius to lay more bricks instead of bigger ones.

All three sit with their base on y=0.

Requires `numpy` and `pillow` (`pip install -r requirements.txt`). About two
seconds per variant; `build/` holds the intermediate texture maps and is safe to
delete.

## What the material actually is

The pillar body has **no textures at all** — just a flat `baseColorFactor` of
`#232529` at roughness 0.35. Earlier versions had full basecolor/normal/roughness
maps with fractal cracks and micro-scratches; the result read as wet photoreal
stone, which is the wrong look. The silhouette and the edge highlights carry it
instead, which is also why the file is 1.8 MB rather than 10 MB.

The only texture in the file is the 256px edge-highlight lookup table. The top
platform's paving used to be three more maps on a separate primitive; it is
real geometry now (see below), so the whole pillar is one primitive with one
material.

## The edge highlight

Every sharp convex edge gets a crisp emissive line of constant *world-space*
width, with no baking, no atlas and no seams. At the current `LUT.plain_color`
it sits about 7.5x brighter than the surface it runs along, so it reads as a
bevel catching light — clearly visible on a pale background too. Set
`plain_color` to `[0, 0, 0]` to switch edges off entirely and leave only the
cracks glowing; `validate.py` reports which state you are in either way.

The trick: distance from a point to a straight edge is **linear** across a
triangle, so it interpolates exactly through the rasteriser as a vertex
attribute. For each triangle we find its sharp convex edges (dihedral angle
above `EDGES.min_angle`, neighbour's free vertex behind the plane), then store
each vertex's perpendicular distance to the two nearest ones in `TEXCOORD_1`,
divided by the band width.

A 2D LUT turns those two distances into the falloff curve, sampled with
`CLAMP_TO_EDGE` so anything past the band reads as zero — which is what makes
unclamped per-vertex distances safe. Sharper edges get a proportionally wider
band, so blunt creases produce thinner lines.

Two slots per face. Sharp edges alone never exceed that, but a face carrying a
crack as well can want a third; the crack always takes slot 0, so a glow line is
never broken to preserve an ordinary highlight.

Because it drives `emissiveTexture`, the lines stay visible on faces turned away
from the light, which is what keeps the geometry readable in shadow.

## The glowing lines

**No geometry is added for these.** No tubes, no strips, no extra vertices — the
cracks are line segments that exist only as numbers in UV1, drawn by the same
mechanism as the edge highlights. (Triangle count goes *down*, not up — see the
sparkle section, where buried faces get removed.)

Three things make that work.

**Packing type into the distance.** There is only one emissive texture, so the
edge *type* has to travel inside the same number as the distance. An ordinary
edge maps to `plain_peak * (1 - d/w)` — peak on the edge, falling toward 0 — and
a glow edge maps to `glow_peak + (1 - glow_peak) * d/w` — peak on the edge,
falling toward 1. Each type therefore occupies its own half of the LUT axis and
runs off toward a texture border where the LUT is zero, so `CLAMP_TO_EDGE` still
handles everything outside the band and the stored values stay linear. The gap
between `plain_peak` and `glow_peak` is dead space that nothing samples, so the
two profiles can never bleed into each other. `validate.py` asserts no value
lands in that gap, and that no single face mixes types within one slot.

Each profile also plateaus at its peak across the gap rather than dropping to
zero there. Without that, the bilinear tap next to the peak reads a neighbour of
zero and every line core comes out at half brightness.

**Choosing where they go (`cracks.py`).** The first version lit up the mesh's
own sharp edges, and that was the wrong shape of thing entirely. A mesh edge is
by definition the *boundary between two faces*, so an edge-locked line can only
trace the outline of the blocks. It read as glowing trim on the corners, it
zigzagged with whatever tessellation the modeller happened to use, and on a
convex corner you see it edge-on from most angles. The reference art does the
opposite: its cracks run *across* faces, straight for long stretches, jogging
sideways occasionally, ignoring the geometry underneath.

Worth noting why the obvious alternative does not work: lighting *concave* edges
instead would put the glow down in the recessed channels, which is where the
reference's brightest lines sit. But this mesh has 169 concave sharp edges and
**not one of them is vertical** — the channels are gaps between separate rib
boxes, not creases in a surface, so there is no edge there to light.

So cracks are generated as free polylines with no relationship to the triangles:
walk downward in short steps, occasionally step sideways a few degrees and carry
on down. They are then snapped onto the nearest real surface, because a path
placed at the outer radius alone floats in mid-air wherever it crosses a
recessed channel and the line simply vanishes there.

They are still drawn by the same UV1 distance packing as the edge highlights —
that machinery never cared whether a line was a real edge, only that it is a
straight segment in space — so they stay crisp at any zoom and keep a constant
world-space width. A face picks up a crack when part of it lies within the band
*and* the crack sits close to that face's own plane; the plane test is what stops
a crack on one rib lighting up the rib behind it.

**Fading the ends.** Each run reports the height range it covers, and every
vertex gets a fade from how close it sits to either end. This needs no extra
channel: the LUT profile already runs from full brightness at 0 to nothing at 1,
so pushing the sample further along that curve dims *and* thins the line by the
same amount.

The fade is **added** to the distance term, not mixed with it. Mixing
(`fade + (1-fade)*t`) looks reasonable but is badly wrong: a vertex past the end
of the run reports "band limit" no matter how far it sits from the edge, so the
falloff spreads across the entire face and floods it with light instead of
drawing a line. The fade is also evaluated at each vertex's projection onto the
edge rather than at the vertex itself, so all three vertices agree on where
along the run they are and the stored value stays linear in distance — which is
what keeps the line thin.

**Making it actually glow.** Two parts.

An 8-bit emissive texture caps at 1.0, so brightness rides on
`KHR_materials_emissive_strength` (currently x8). Because the strength
multiplies the whole texture, `plain_color` in config is the *final* intended
value for ordinary edge highlights and gets divided by the strength when the LUT
is written — otherwise turning up the glow would blow out every ordinary edge
with it.

Brightness alone still reads as a painted stripe, so the glow profile is three
parts rather than one curve: a hot near-white core, a saturated blue line, and a
broad dim halo spreading onto the surrounding stone. The halo is standing in for
the bloom a real engine would add, so the asset reads correctly even in a viewer
with no post-processing. Its reach is bounded by `GLOW.band` — rib faces are
about 0.19 wide, and past roughly 0.07 the halo floods entire faces and the
lines turn into blobs.

Set `EDGES.emissive` to `[0, 0, 0]` to kill all emissive, or `GLOW.paths` to 0
for crisp edges with no glow.

## Retired: the top cap overhang

The old source mesh had a problem the generated shell cannot have. Its top
outward flare (the "haunch") reached r=0.899 while the crenellation ring dropped
on top of it only reached 0.844–0.888, so at 14 of 48 angular positions the
haunch poked out past the platform and broke the silhouette. `reshape.py` solved
for the smallest XZ scale that lifted the cap clear everywhere and applied it in
memory at build time.

The ring is no longer a separate object sitting on a separate haunch — both are
rows of the same radius field, and the ring starts at exactly the deck radius by
construction. `TOP_CAP.enabled` is `False`, and `validate.py` only runs the
overhang assertion when it is on. The code is kept because it still works if
some future shape needs it.

## Retired: mesh vs texture on the top

The platform used to be a split thing: a flat disc of geometry carrying
basecolor/normal/roughness paving *textures*, ringed by real blocks. That
split caused its own bugs — the face-selection pass that decided what was
"platform" once painted brick onto the haunches — and it hard-baked the brick
size: scale the pillar up and the bricks scaled with it, so the huge variant
had comically large bricks instead of more of them.

The paving is real geometry now (`shape._paving`), on the same material as
everything else, and the whole selection problem is gone along with the three
texture maps and the second primitive.

## Why triangles were showing up on flat panels

In plain terms: the model is built out of four-sided panels, but graphics
hardware only draws triangles, so every panel gets cut in half along a diagonal.
The generated shell keeps every quad exactly planar, which removes this at the
source, but the profile still curves from row to row and neighbouring panels
still meet at a few degrees.
Where a panel's four corners are not *perfectly* flat, the two halves end up
tilted very slightly differently. Each triangle was being shaded
as its own flat facet, so those two slightly different tilts caught the light
differently and the cut line between them became visible. That is the triangle
you could see.

The fix is to let neighbouring triangles share a single averaged surface
direction wherever the bend between them is below `SHADING.smooth_deg` (28°), so
the pair reads as one continuous panel again. Anything that bends more than that
is a genuine crease and stays perfectly sharp, which is what keeps the blocky
silhouette. Tangents are rebuilt against the smoothed normals to match.

One consequence of generating the mesh is that this now has real work to do in
the other direction as well: a rib's panels follow the profile curve row by row,
bending a couple of degrees each time, and smoothing is what turns that stack of
facets back into one continuous curved surface. Roughly 7600 of the 10700 shared
edges qualify.

The texturing pass wants three vertices per triangle, not a welded surface: UV1
holds each corner's distance to *its own face's* sharp edges, which is a
different number for every face meeting at a vertex. `shape.build` therefore
splits the welded surface back apart on the way out. Handing the pass shared
vertices makes those per-vertex writes collide and the winner is arbitrary —
normals come out flipped and the edge lines smear across whole faces, which is
exactly what it looked like the first time.

## Fixing the sparkle

Several separate causes, found by `python scan_mesh.py`:

**Coincident surfaces (the big one) — solved at the source.** The old mesh was a
union of overlapping boxes that were never booleaned, so ~40% of its faces sat
buried inside the solid, many exactly coplanar with a visible face. Two surfaces
at identical depth flicker against each other as the camera moves, and no amount
of MSAA fixes it.

That used to be treated downstream: `reshape.remove_buried_faces` hunted the
buried ones with a generalized winding number (plain ray-parity does not work on
a union of overlapping shells — a point inside two of them gets an even crossing
count and reads as outside) and deleted 3159 of 7920 triangles, then
`break_coplanar_ties` nudged one face of each of the 862 remaining flush pairs
inward by a hair to give the depth test a stable winner. It worked, and it cost
most of the build time.

The generated shell emits every face exactly once and never emits an interior
one, so there is nothing to find. `BURIED.enabled` and `ZFIGHT.enabled` are both
`False`; a whole-pipeline run went from about a minute to two seconds.
`validate.py` still asserts zero coincident coplanar pairs, and `scan_mesh.py`
still reports the census, so a regression here would be loud.

**Mortar lines.** In the texture era these were thin hard-edged shapes that
aliased into beaded dots at grazing angles, and got supersampled 3x to cope.
Retired outright: the paving is geometry now and its joint lines are the edge
highlight, which is already anti-aliased by construction (it is a smooth ramp
sampled per pixel, not a picture of a line).

**The glow core.** It was 0.007 world units wide, about one pixel at normal
viewing distance, which is precisely when a hard-edged feature stair-steps. It
is now 0.018 units with a softer falloff.

**The LUT sampler.** The edge LUT is a ramp, not a picture, and UV1 sweeps a
huge range across a single face. With mipmaps the derivative is large enough
that the GPU would collapse the entire falloff curve into its average, and blur
the ordinary and glow profiles into each other across the dead zone. It now
samples LINEAR with no mipmaps, asserted in `validate.py`.

`scan_mesh.py` on the current output: 0 degenerate triangles, 0 slivers, 0
duplicate faces, 0 coincident pairs, 0 boundary edges, 0 edges with inconsistent
winding. The old mesh carried 41 inconsistently-wound edges and 2433 boundary
edges left behind by the burial removal.

## The top platform

Real bricks, no texture, and it is the entire top of the pillar — the disc
runs flush to the outer edge, directly on top of the shaft. Outside in: a
flush kerb ring exactly on the deck plane, concentric courses of bricks, and a
round centre stone. The kerb is not decoration: the shell's top edge is a
polygon of chords between its 65 columns while brick corners sit on the true
circle, and one ring sampled at the shell's own angles is what bridges the two
without cracks. Brick size is
fixed in **world units** (`SHAPE.paving`), so course count and bricks per
course are derived from the final platform radius — the base pillar lays 5
courses, the huge one 14, at the same brick size. The build prints the platform
face count per variant so the scaling is visible in numbers.

There is no mortar geometry either. Each brick drops below the deck plane by a
small multiple of `paving.drop`, chosen so every brick differs from all of its
neighbours: courses alternate between the {0,2} and {1,3} step sets, bricks
alternate parity within a course. Every joint is therefore a real step, every
step is a sharp edge, and the same edge highlight that outlines the shaft
blocks draws the joint lines — which is what makes the platform read as part
of the same object instead of a decal.

Watertightness follows the same two rules as the shell, in disc coordinates.
Any circle shared by two courses is sampled at the union of both courses'
joint angles, so their two polygonal approximations of that circle are the
same polyline — different brick counts would otherwise leave crescent cracks
between the chords. And each vertical edge where four bricks meet is split at
all four brick heights, the shell's corner rule again. The outermost circle is
the hole `mesh_field` leaves open at the deck, sampled at the shell's own
column angles with bit-identical arithmetic, so paving and shell weld into one
closed surface — `validate.py`'s zero-boundary-edges assertion covers the seam.

Joints in adjacent courses are also kept staggered: a purely random course
offset occasionally lands a joint within a ten-thousandth of a radian of one
in the course outside it, making two radial walls coplanar in the same plane
through the axis — a z-fight at the touching corner, and visually one long
crack across the courses, the thing real paving staggers its joints to avoid.

## A note on the preview renderer

`raster.py` exists because previews that lie are worse than no previews. An
earlier version shaded flat facets and ignored the normal map entirely, so the
generated previews looked clean while the real asset was covered in speckled
micro-detail in an actual engine. It now does tangent-space normal mapping and
GGX specular, and `render_preview.py` reads geometry, materials and textures
back out of the exported glb rather than reusing the build script's in-memory
state — so a preview reflects the file, not the intent.
