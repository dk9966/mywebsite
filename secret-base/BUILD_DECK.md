# Editing the islands

> Editing in Blender's interface instead of in the script? See
> [EDITING_BY_HAND.md](EDITING_BY_HAND.md).

Everything on top of the pillars is generated by [`build_deck.py`](build_deck.py).
Nothing is modelled by hand. You change numbers in the script and re-run it.

## Re-running

In Blender's Text Editor, or the Python console:

```python
exec(open("/Users/danielku/mywebsite/secret-base/build_deck.py").read())
```

It wipes the `deck_huge` and `deck_workshop` collections and rebuilds them from
scratch, so **anything you move by hand inside those collections is lost on the
next run.** That's the trade: you get repeatable, tweakable geometry, but the
script is the source of truth. Move things by editing numbers, not the viewport.

(The pillars themselves live outside those collections and survive — except
`island_pillar_workshop`, whose position is set by `clone_pillar` on line 1052.)

## The coordinate system

Everything is placed in **polar coordinates** around the centre of its own
pillar: an angle, a radius, and a height.

```
a   angle in radians. D(deg) converts: D(56) is 56°.
    0° = +X.  The back wall is centred on 56°.  The camera looks in from 238°.

r   radius from the deck centre, in metres.
    LARGER  = further out, toward the rim and into the wall
    SMALLER = further in, toward the middle of the deck

h   height in metres above the deck floor.
```

Two constants do most of the work:

| Name | Value | Meaning |
| --- | --- | --- |
| `R` | 2.78 | deck radius — the outer edge |
| `F` | floor level in world Z | the deck surface |

**Write outer things as offsets from `R`, not as absolute numbers.** The railing
is at `R - 0.068`, the wall's inner face at `R - 0.10`. That way changing `R` on
line 23 moves the whole rim, railing, wall, shelving and furniture together
instead of leaving them stranded.

Some helpers take `h` (relative to `F`) and some take absolute Z (`F + h`). The
table below says which.

## The drawing helpers

| Helper | Makes | Z convention |
| --- | --- | --- |
| `polar(a, r, h)` | a *position* at angle/radius/height | relative (adds `F`) |
| `box(bm, pos, size, rz)` | a rectangular block | absolute (use `polar`) |
| `tube(bm, r0, r1, z0, z1, a0, a1, seg)` | a curved band / ring / disc | absolute |
| `revolve(bm, profile, a0, a1, seg)` | sweeps an `(r, z)` outline around the centre | absolute |
| `rev_at(bm, cx, cy, profile, seg)` | same, around any vertical axis | absolute |
| `slab(a, cr, z0, z1, dep, wid, key)` | a block, by height range *(workstation only)* | relative |
| `ring(a, rr, z0, z1, r0, r1, key, seg)` | a ring around a local axis *(workstation only)* | relative |
| `finish(name, bm, material)` | turns a bmesh into a real object | — |

### box sizes are (radial, tangential, vertical)

When you pass the item's own angle as `rz`, its local X points outward:

```python
box(bm, polar(a, R - 0.30, 0.84), (0.30, 0.22, 1.36), a)
#                                   ^depth ^width ^height
```

`box` can only rotate about Z. There is no tilt. To fake a canted surface,
stack thin slats each stepped slightly in radius — that's how `mod_console`
builds its angled control face (line ~370).

### tube is the workhorse

```python
tube(bm, 2.10, 2.26, F + 0.2, F + 1.5, D(26), D(86), 32)
#        inner outer  bottom   top      from   to    segments
```

Omit the angles for a full circle. Set `r0 = 0` for a solid disc. More segments
= smoother curve, more faces.

## Worked examples

**Resize a display panel.** The screens live in three groups. The main one on
the back wall is `DISPLAYS` (line 441) — one row per panel,
`(angle offset in degrees, width, height, height of centre)`:

```python
DISPLAYS = ((0.0,   1.30, 0.82, 1.18),     # the big central one
            (-25.0, 0.44, 0.26, 1.80),     # the row above it
            ...
```

The two freestanding side clusters are `SIDE_PANELS` (line 467), same four
columns, but the angles are relative to their cluster. `SIDE_CLUSTERS` on line
465 says where each cluster stands, and `SIDE_R` how far in from the rim.

Watch the ceilings: the wash bar sits at `1.972` and panels must clear the desk
at `0.585`. To go taller, raise the gantry first — masts, truss chords and wash
bar are lines ~410–423.

**Space the screens out differently.** Widths are in metres but gaps are in
degrees, so the same gap looks bigger the further out you go. At the main
array's radius one degree is about 4 cm; out at the side clusters it is 3 cm.
If two panels overlap after you widen one, push the neighbour's angle out
rather than shrinking it.

**Change the desk height or thickness.** Two constants at the top of the
workstation block (line ~396):

```python
DT  = 0.50      # height of the top surface above the floor
DTT = 0.10      # thickness of the top slab
```

Everything on the desk — emitters, keyboard, mouse, mug — is written relative
to `DT`, so raising or lowering it carries the whole setup with it. The legs
and fascia are separate though: if you change `DT` by a lot, adjust the leg
height on the next few lines or they will float or poke through.

**Move the speakers.** Line ~467:

```python
for sa in (SA0 - D(5.5), SA1 + D(5.5)):        # angle: further from the desk
    box(gm, polar(sa, R - 0.44, 0.360), (0.20, 0.24, 0.72), sa)
    #                     ^radius  ^centre height   ^depth ^width ^height
```

Raise `0.72` and the cabinet gets taller, but `0.360` is its *centre*, so raise
that to half the new height or it will sink through the floor.

**Widen the deck.** Change `R` on line 23. Everything keyed to `R` follows. The
pillar top underneath is only 2.24 across, so the extra hangs on the corbel
courses at line ~175 — widen those too if you go much past 2.9.

**Change the floor rings.** Line ~553. There is no table of radii any more —
the rings run in the joints between paving courses, so section 1 decides where
they *can* go and section 4 picks which ones light up. `RINGS` is how many;
`w` is the strip width; the four `grnd.uniform` ranges under it set how broken
each ring is, and seed `77021` on the line above redraws the scatter.

`RIM_CLEAR` holds the outer ring back off the kerb, by dropping any joint
within that distance of the paving edge before anything is chosen. Without it
the outer ring sits right under the fence. It is also the knob for how tightly
the whole pattern sits: raising it drops another joint off the outside, and the
even-spacing search then rebalances all four rings inward rather than moving
only the last one.

The rings are meant to be evenly spread, but they also have to sit in a joint
and the joints are not evenly spaced, so the two pull against each other. The
outermost rings are pinned to the first and last usable joint and the inner
ones are searched for, taking whichever combination makes the gaps closest to
equal. Do not replace this with snapping each evenly-spaced target to its
nearest joint: that picks the nearest joint to each target, which is not the
same as the most even set, and it leaves one gap noticeably short. Some
unevenness survives regardless — with the current seed and `RIM_CLEAR`
the gaps are 0.53 / 0.56 / 0.55, and that is the best any four of those joints
can do.

The strips use `runeGlow`. Its brightness is pushed in blue and nowhere else:
see the bloom note below for why.

**Change how much the rings bloom.** Bloom is the compositor glare at line
~1130 — EEVEE has had no built-in bloom since 4.2 — and it is coupled to
`runeGlow`. Three things matter:

- `Size` is a fraction of the *frame*, not of the object. Small values (~0.25)
  make the glow hug the line, which is what reads as bloom. Large ones smear the
  whole render into flat fog and look like nothing at all.
- `Threshold` is scene-linear radiance. It has to sit under the peak of anything
  meant to bloom — `runeGlow` reaches 1.5 in blue — and above the lit paving, or
  the floor hazes over.
- `runeGlow` has to be bright enough to clear that threshold, but pushed in blue
  only. Any real green in the emission goes white the moment it passes 1.0 and
  the rings turn into hot scratches; blue alone stays blue through AgX while
  still carrying the energy the glare needs.

Do not fake the glow with a second, wider band of geometry. It reads as two flat
colours at any distance the camera actually gets to.

`GZ1` is the one number to leave alone: the strips fill their joint flush with
the stones either side, and dropping it lower hides the outer rings behind the
stones at grazing camera angles.

**Change the paving.** Line ~189. The floor is concentric courses of flagstones,
each course starting at its own random angle so the radial joints stagger
instead of lining up into spokes. `pav.uniform(0.135, 0.215)` is the course
depth, `pav.uniform(0.17, 0.40)` the stone width in metres, and the last
`pav.uniform` the stone thickness — that is what makes the joints read. The
`0.007` minimum inset is load-bearing: it is what guarantees every stone leaves
enough joint for a section 4 strip. Seed `4471` above redraws the lot.

## Designing a new shape

The workstation machinery is the model to copy: small builder functions you
call at different angles with different numbers. A minimal one:

```python
def mod_pod(a, top, wid=0.24, dep=0.30, br=None):
    br = PIER_R if br is None else br      # which wall to stand against
    cr = br - dep / 2                      # centre radius of the body
    slab(a, cr, 0.00, 0.12, dep + 0.06, wid + 0.08)          # plinth, oversized
    slab(a, cr, 0.12, top - 0.10, dep, wid)                  # body
    slab(a, cr, top - 0.10, top, dep * 0.7, wid * 0.7)       # tapered cap
    slab(a, cr - dep / 2 - 0.006, 0.30, top - 0.20,
         0.012, 0.030, "neonCyan")                           # strip on the front face
```

Then call it: `mod_pod(D(15), 1.4)`.

Three rules that keep new shapes looking like they belong:

1. **Step the silhouette.** A plinth slightly wider than the body, a cap
   slightly narrower. Three steps reads as designed; one box reads as a box.
2. **Put the light on a face, not the whole object.** A thin emissive strip at
   `front face - 0.006` catches the eye without washing out.
3. **Vary the height, keep the language.** The towers, drum and console share
   materials and detail sizes but are 2.15 m, 1.10 m and 0.74 m tall. That
   contrast is what stops the back wall reading as one rectangle.

To put a shape on its own object instead of merging it into a material group,
build it in a fresh bmesh and finish it:

```python
bm2 = bmesh.new()
box(bm2, polar(D(40), R - 0.5, 0.4), (0.3, 0.3, 0.8), D(40))
finish("deck_my_thing", bm2, "graphite")
```

## Materials

Names in `MATS` (line 31) are meaningful: the web app swaps materials **by
name** at GLB load time, so `graphite`, `neonCyan`, `lampWarm` etc. get replaced
by the live versions in `components/scene/materials.ts`. Names not in that
registry — like `displayPanel` — pass through untouched, which is why the
placeholder screens use one.

Emissive strength is the dial to reach for. The view transform is AgX, which
desaturates anything very bright toward white, so **a dim saturated emitter
reads more colourful than a bright one.** If a glow looks washed out, turn it
down rather than up.

## Gotchas

- **Radius direction.** Larger radius is *away* from the deck centre. Building
  a shelf back-to-front is easy to do and looks fine until you notice every
  bottle is inside the wall.
- **Two islands, one script.** `finish` and `light` append `suffix` to every
  name, so the workshop's objects all end in `_b`. Any code that looks an object
  up by name has to add the suffix too.
- **Angles are radians.** `D(45)`, never `45`.
- **Overlaps don't error.** Two objects in the same place just render as a mess.
  When you move something, check what was already there.
